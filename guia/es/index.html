Qué es

Una skill que audita tu configuración — y no la toca

Cada línea de tu configuración es culpable de complejidad hasta que se demuestre su utilidad. La skill lee todo, clasifica cada instrucción y entrega un informe con la versión mínima propuesta. Aplicarla es decisión tuya, en una solicitud aparte.

🔍 Diagnóstico completo

Clasifica cada instrucción como contexto, guardrail, criterio, verificación, integración, procedimiento, microgestión, redundancia, legado o no comprobada.

🔒 Solo lectura

Ninguna edición, ningún rm, ningún mv, ningún commit. Una auditoría que ya empieza a hacer cambios es una auditoría en la que no confías.

🧪 Plan de pruebas

Termina con un plan de ablación A/B/C sobre tareas reales de tu proyecto — para comprobar el cambio antes de adoptarlo.

La visión

Por qué Claude Code borra su propio prompt

Boris Cherny creó Claude Code en Anthropic. La tesis, en una frase: la configuración envejece.

Cada ~6 meses y, sobre todo, cuando se lance un modelo importante: elimina tu CLAUDE.md, elimina tus skills, elimina tus hooks — y mira qué hace el modelo sin ellos. Boris Cherny · charla en Y Combinator, un día después del lanzamiento de Opus 5

La configuración es una solución fechada

Cada instrucción que escribes corrige la debilidad de un modelo específico. Cuando el siguiente modelo ya no tiene esa debilidad, la línea se convierte en peso muerto — y se sigue volviendo a leer en cada uso.

Más del 80% eliminado

Eso fue lo que pasó en el propio Claude Code con la llegada de Opus 5. Lo que quedó del prompt del sistema es casi todo seguridad, permisos, análisis estático e interfaz.

Especificar demasiado es el error común

Escribir instrucciones como «haz A, luego B y después C» funcionaba con los modelos antiguos. Hoy impide que el modelo encuentre un camino mejor. Escribe la tarea + los límites de seguridad + los criterios de salida.

La verificación es la palanca

Un prompt corto con una forma real de que el modelo verifique su propio trabajo supera a un prompt gigante sin verificación. Producir → observar → comparar → condición de parada.

La reconstrucción en 4 etapas

1. Elimina la configuración→ 2. Úsala en trabajo real→ 3. Observa dónde tropieza→ 4. Devuelve solo lo que falló 2×

La cuarta etapa es la que importa: predices muy mal qué instrucción necesita el modelo, y cada línea que conservas consume contexto en cada ejecución.

Por qué hacer la limpieza

El sedimento que todos acumulamos

Si usas Claude Code desde hace algunos meses, probablemente tengas al menos tres de estos:

SíntomaLo que suele ser
CLAUDE.md de 300 líneas con excepciones fechadascorrecciones de modelos que ya quedaron obsoletas
La misma regla en CLAUDE.md y en 3 skillsredundancia que se convierte en conflicto cuando cambia una de las copias
Skill de 400 líneas que enseña «cómo pensar»razonamiento genérico que el modelo ya hace por sí solo
Paso a paso rígido de 12 etapasmicrogestión que bloquea la mejor ruta
Dos reglas que se contradicenel modelo elige una, y no sabes cuál
Nada que diga cómo verificar que quedó bienel agujero más costoso de todos

El costo es compuesto: contexto consumido en cada llamada, autonomía reducida, comportamiento inconsistente y reglas zombi que nadie borra porque ya nadie recuerda qué están sosteniendo.

El objetivo no es maximizar la reducción. Es maximizar calidad + autonomía + verificabilidad ÷ complejidad — por eso la skill conserva explícitamente lo que el modelo no puede inferir: identidad del proyecto, rutas y fuentes de verdad, branding, seguridad, compliance, integraciones y contratos de interfaz.

Cómo funciona

Inventario → clasificación → decisión → informe

Cada instrucción recibe una categoría y una decisión. Sin evidencia suficiente, la skill prefiere TEST a KEEP.

Leer CLAUDE.md + skills + hooks→ Clasificar cada instrucción→ Decidir KEEP/SIMPLIFY/MOVE/MERGE/TEST/REMOVE→ Auditar skill por skill→ Informe en 10 secciones

Guía de uso · paso a paso

Instalar y ejecutar

Skill autocontenida: un archivo SKILL.md. Sin dependencias, sin build.

1

Clona el repositorio

O SKILL.md queda en la raíz — la instalación es un cp.

git clone https://github.com/inematds/audit-ablacaocc.git
2

Instálala como skill global

Aplica a todos los proyectos de tu máquina.

mkdir -p ~/.claude/skills/audit-ablacao
cp audit-ablacaocc/SKILL.md ~/.claude/skills/audit-ablacao/SKILL.md
3

…o solo dentro de un proyecto

Así, la skill se versiona junto con el código y no se filtra a los demás proyectos.

mkdir -p .claude/skills/audit-ablacao
cp /caminho/audit-ablacaocc/SKILL.md .claude/skills/audit-ablacao/SKILL.md
4

Reinicia la sesión y llama directamente a

La invocación explícita elimina la lotería del disparador.

/audit-ablacao  # o: "haz una auditoría de ablación de mi CLAUDE.md global"
5

Elige el alcance

Global cada ~6 meses o con el lanzamiento de un modelo; por proyecto cuando el CLAUDE.md supera ~150 líneas; por conjunto de skills cuando 3+ compiten por el mismo disparador.

/audit-ablacao audita as skills deste projeto # alcance en lenguaje natural
6

Aplícala en otra sesión

La skill no aplica nada — a propósito. Toma el Top 10 por impacto ÷ riesgo, aplícala, úsala en trabajo real durante algunos días y devuelve una instrucción solo cuando se repita el mismo fallo.

# línea de base de ablación usada internamente en Anthropic:
CLAUDE_CODE_SIMPLE=1 claude  # se ejecuta sin ningún prompt de sistema
Consejo aplicado en la práctica

Aprovecha al máximo las skills — invocándolas directamente o dentro de los proyectos

Esta práctica cambia el resultado más que cualquier ajuste del prompt, y es el complemento natural de la limpieza: lo que sale del CLAUDE.md no se pierde, se convierte en skill.

📦 Una skill es un procedimiento, no una regla global

Regla en CLAUDE.md se lee en toda ejecución, incluso en el 90% que no tiene nada que ver con ella. Dentro de una skill, solo consume contexto cuando la tarea corresponde — es el MOVE e o LOAD-ON-DEMAND del informe.

🎯 Invocarla directamente elimina la lotería del disparador

/nome-da-skill no depende de que la descripción coincida con tu frase. Cuando varias skills compiten por el mismo tema, la invocación explícita desempata — y evita una regla de enrutamiento en el CLAUDE.md.

🗂️ Una skill del proyecto se versiona junto con el código

En .claude/skills/, el procedimiento acompaña al repo, entra en el PR, se puede revisar y no contamina los demás proyectos.

🔧 Una skill es la unidad adecuada para corregir

Cuando el modelo tropieza, hay tres remedios: un mejor prompt (instrucción confusa), skill (falta un procedimiento repetible) o MCP (falta contexto inalcanzable). Elegir bien evita el reflejo de volcar otra regla más en el CLAUDE.md.

En la práctica: el CLAUDE.md se queda solo con lo que es verdad siempre — identidad, guardrails, fuentes de verdad, seguridad. Todo lo demás (procedimiento, formato, receta, integración) se convierte en skill, que se invoca directamente cuando sabes qué quieres.

Ciclo recomendado

Ejecutar, recortar, usar, observar, repetir

La ablación no es un evento único. Es mantenimiento.

1 · Ejecutar
Auditoría dentro del alcance elegidoGlobal, proyecto o conjunto de skills.
2 · Recortar
Top 10 por impacto ÷ riesgoEn una sesión separada — la skill no se aplica.
3 · Usar
Trabajo real durante algunos díasNo en una prueba hipotética. Es donde aparece el fallo.
4 · Devolver
Solo lo que falló dos vecesY de la forma más breve posible.
5 · Repetir
Cada ~6 meses o con el lanzamiento de un modeloEl motivo de un fallo antiguo puede haber desaparecido.
Guía práctica

Publicar en Git y en el portal

La receta que siguió este mismo repositorio. Sirve para cualquier skill o proyecto INEMA.

1

Estructura del repo

La guía va en guia/, nunca en la raíz — la raíz es para el código. Y es una página dentro del repo del proyecto, nunca un repositorio separado.

audit-ablacaocc/
├── SKILL.md        # una skill (en la raíz = instalable con un cp)
├── README.md
├── capa/capa.png   # portada 1280x720 (skill capa-inema)
├── guia/index.html # landing + guía autocontenida
└── doc/            # material de base
2

Git — desde cero hasta el push

Revisa el autor antes antes de hacer commit: un autor que no coincide con la cuenta de destino es el motivo nº 1 de que se bloquee el deploy después.

git init -b main
git config user.name  "inematds"
git config user.email "inematds@gmail.com"
git add -A && git commit -m "feat: skill audit-ablacao + guia"
gh repo create inematds/audit-ablacaocc --public --source=. --remote=origin --push
3

GitHub Pages

Crea primero el .github/workflows/pages.yml (YAML completo en el README) — el build legacy "deploy from a branch" se bloquea. Como la guía está en guia/, la URL pública termina en /guia/.

# con .github/workflows/pages.yml en el commit:
gh api -X POST repos/inematds/audit-ablacaocc/pages -f build_type=workflow
gh api repos/inematds/audit-ablacaocc/pages -q .html_url
4

Portal (inema.club)

Cuando la URL de Pages responda, publica en las 3 superficies INEMA — portal, inemabuscas y catálogo PRO.

/atualiza-portal https://inematds.github.io/audit-ablacaocc/guia/
5

Definición de "publicado"

Publicar = commit + push en origin. El deploy es automático mediante webhook git → Vercel / Pages: nada de abrir el dashboard, revisar el estado ni volver a activar el deploy.
